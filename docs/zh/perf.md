# 性能基线（ox 0.4）

以下数字来自单台 Linux 机器（CPython 3.12、回环网络、/tmp 在内存盘），
是**数量级参考**而非承诺——用途是让你能对自己的负载心里有数。在仓库
根目录执行 `python scripts/bench_ox.py` 可复现。

| 基准 | 耗时 | 说明 |
|---|---|---|
| 启动（空程序） | ~256 ms | 进程创建 + 运行时初始化 |
| fib(26)，解释器 | ~3.8 s | 树遍历求值器，CPU 密集 |
| fib(26)，编译产物 | ~1.1 s | `ox build` 输出，快约 3.4 倍 |
| 1k 并发 spawn 任务 | ~278 ms | 扣除启动净开销约 20 ms |
| 10 MB 文件写+读 | ~265 ms | fs 层，大头是启动 |
| 1 万对象 JSON 往返 | ~390 ms | 解析 + 序列化 |
| 2 万条 f 字符串 + join + upper | ~392 ms | 字符串层 |
| 2 万次 push/map/filter | ~542 ms | 列表层 |

## 怎么读这些数字

**小脚本被启动开销支配。** 每次运行约 250 ms 花在 Python 进程创建和
ox 运行时初始化上。低于十万级操作量时，语言层开销相对启动基本可以
忽略——与其跑很多小脚本，不如让一个脚本多干活。

**解释器是树遍历的。** CPU 密集的递归是"脚本语言速度"（fib(26) 约
3.8 秒）。用 `ox build` 编译后转译为原生 Python 协程，同一程序快约
3.4 倍——热循环先编译：

```console
$ ox run hot.ox      # 解释执行（I/O 密集的自动化足够）
$ ox build hot.ox    # 编译（CPU 密集值得）
```

**I/O 与数据处理是 Python 速度。** 文件、JSON、字符串、列表操作直接
在标准库层运行（很多经线程挪出事件循环），成本与等价 Python 相当。
并发本身是 asyncio 任务：1k 个 spawn 任务只比空程序多约 20 ms。

**服务器面向自动化规模流量。** 内置 HTTP 服务器是手写的 asyncio 协议
实现——适合内部工具、健康检查、仪表盘。它不是高并发场景下的生产级
WSGI/ASGI 替代品；需要高扇入时请前置真正的反向代理。

## 已知上限（刻意设计）

- **没有 NaN/Infinity**：除零永远抛可捕获错误。
- **递归上限**：解释器约 900 层（编译产物更宽松）——超深递归干净
  报错，病态深度请改写为循环。
- **请求/响应体上限 32 MB**（`serve`，超出返回 413）。
- **单核调度**：ox 是单个 asyncio 循环；CPU 密集并行需要 `os.start`
  （子进程），而不是线程。
